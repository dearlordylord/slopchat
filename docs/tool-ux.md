# OpenCode V2 tool UX

Investigated official `anomalyco/opencode` V2 source on 2026-10-08. `git ls-remote` and the checkout resolved `v2` to `f5309982d01ac72c63fc1b563bebb1e6febfd4b5`. This research uses that revision; SlopChat's palette attribution pins an earlier revision, `5b312918ecd673fdcc76094471a87067f0fa36e7`. Findings concern the terminal UI in `packages/tui`, not the web application.

## What upstream actually renders

- **Structured parts and a stable tool ID.** Tool input starts as a `streaming` part, becomes parsed input in `running`, receives progress metadata, and ends as `completed` with content or `error` with an error object. Creation, execution and completion timestamps stay on the same part. Text and reasoning have separate events and renderers. [Client event reducer](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/client/src/solid/data.ts#L910-L994).
- **Tool-specific presentation.** The TUI dispatches by canonical tool name. Unknown tools get a compact summary and a click-to-expand list of input fields and plain output. It does not automatically syntax-highlight arbitrary tool output. [Dispatch and generic renderer](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L2406-L2634).
- **Shell and read differ.** Shell has a command/output block, spinner, working-directory prefix, a roughly ten-line collapsed budget, and expansion; background shell output is fetched separately. Read is a compact path/range row plus loaded-file notices, not a highlighted copy of the file contents. [Shell](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L2813-L2985), [read](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L3036-L3075).
- **Edits carry real patches.** The edit renderer consumes structured file/patch metadata, chooses unified or split view (automatic split above 120 columns), and supplies syntax style, line numbers, wrapping and addition/deletion colors to `PatchDiff`. [Edit renderer](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L3277-L3349).
- **The closest match to dynamic Lisp evaluation is `execute`.** It shows a compact execution row, child calls from `metadata.toolCalls`, and an error preview. Clicking opens a live detail dialog with separate Code and Output blocks, state/duration, highlighted TypeScript code, and JSON highlighting only when parsing succeeds. The dialog offers arrow/page/home/end scrolling, `c` to copy code, `o` to copy output, and mouse copy buttons. [Execute row](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L3230-L3275), [detail dialog](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/dialog-execute.tsx#L19-L282).
- **Prose and selection are separate concerns.** Assistant prose uses a streaming Markdown renderer with syntax style and grid tables. Tool click handlers check for selected text before toggling. Selection supports copying and Escape clearing; optional drag-release copying retains selection. [Markdown](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/message-parts.tsx#L166-L195), [selection guard](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/routes/session/index.tsx#L2687-L2697), [selection behavior](https://github.com/anomalyco/opencode/blob/f5309982d01ac72c63fc1b563bebb1e6febfd4b5/packages/tui/src/util/selection.ts#L34-L100).

## Application to SlopChat

Recommendations, not implemented changes:

1. Keep the single dynamic evaluation tool. Give it a compact summary/status row and an expandable or modal detail view with **Lisp code**, **result**, and explicit errors. Use Markdown for assistant prose; use code rendering with a configured Emacs Lisp grammar for expressions. Keep arbitrary result text literal unless its format is explicit or successfully parsed.
2. Preserve canonical memory text. Add optional presentation metadata: stable `callId`, `parentCallId` for nested evaluations, tool name, expression, lifecycle status, start/end timestamps and explicit error. Associate output chunks with `callId`; retain chunk ordering if logging splits large messages. Do not pair adjacent tool/result rows: nested evaluations make adjacency ambiguous.
3. Make collapsed previews reversible: indicate hidden content, provide full detail scrolling and separate copy-code/copy-result actions. Do not use a display limit as the stored-content limit. Avoid opening/collapsing a card after a text-selection gesture.
4. Add shell/read/diff specialization only when execution emits real operation metadata (command/workdir/exit, file/range, or before/after/patch). Arbitrary Lisp can perform several operations; guessing these from expression or result text would misrepresent execution. Optional structured child-operation events can later provide an `execute`-style view without changing the model-facing tool API.
